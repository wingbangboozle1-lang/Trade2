#ItemWhat is unverified or irregularEffect on the siteSource to review
F1 No Kalshi demo account could be provisioned Demo signup requires an email inbox that can receive a verification message; no mailbox is available in this environment. The signed order client (POST /portfolio/events/orders) and the account portfolio reads (balance, positions, fills, settlements) are implemented and unit-tested against the documented request format, but have never been executed against a real Kalshi account. Every trade, position and P&L figure on the site comes from the simulated engine and is labelled as such. No page claims a real filled order. The “Kalshi demo account” portfolio view is therefore blank rather than filled with simulated numbers pretending to be account data. Kalshi: creating and using a demo account · Create Order (V2) · Get Portfolio Balance
F2 GET /events ignores the category filter A live request with ?category=Crypto returned events whose own category field was "World". The documented filter is not applied by the service. Topic classification is done locally from series and market titles. Kalshi's own category strings are stored exactly as returned and are never edited. Get Events
F3 Demo content is not identical to production Kalshi states that demo prices and behaviour “may not be reflective of those in real markets”. Observed demo tickers include demo-only strike names (for example KXNEWPOPE-70, KXNEXTNATOSECGEN-99), and many demo books are quoted with little or no resting size. Every result on the site is a demo-environment result. Nothing here should be read as a claim about production behaviour. Demo environment
F4 Browser → Kalshi direct calls are not confirmed to be permitted No official Kalshi statement about CORS on the public REST endpoints was found. The dashboard therefore reads the committed snapshot by default; the “Try live browser API” button tests the browser's own policy and reports the result rather than assuming it works. The live view is a graceful upgrade, not a dependency. Every feature works from the published snapshot. Quick start: market data
F5 “Dollar amount” is our construction, not a Kalshi-published metric Kalshi publishes open interest in contracts and prices in dollars. The site multiplies them to show notional; the traded-notional column uses volume × price. Both columns are labelled with the formula in the methodology page. No Kalshi field is presented as a dollar amount. Get Markets · Fixed-point representation
F6 Attribution of a swing is not verifiable automatically The API reports what a market settled on and which sources Kalshi lists for it; it does not report what moved the price. The site links the official settlement sources as candidates for the catalyst and never asserts a cause. Chart markers and chat messages link the Kalshi market page and the published settlement sources instead of naming a headline. Get Event
F7 Fees are not modelled in the simulation The published fee schedule is not part of the market response used here, so the simulated P&L is gross of fees. Simulated returns are an upper bound. No fee figure is displayed because none could be confirmed for each market from the data collected. Fee rounding
F8 Resolution tracking depends on Kalshi reporting a result Demo markets rarely settle during the life of this project. Positions settle only when the market's result field becomes yes or no. Most simulated positions remain open and are marked to the live bid; the resolution column stays blank until Kalshi reports one. Market settlement · Market lifecycle
F9 Candle history in the demo environment is short The 1-minute candle route returns roughly six hours of data for demo markets, and the batch candle route answers with a markets array rather than a candlesticks array. The intraday chart uses the 1-minute series and the trade feed; the backtest uses hourly candles, which return a longer window. Get Market Candlesticks · Batch Get Market Candlesticks
F10 Batch orderbook parameter handling differs from the SDK Requesting /markets/orderbooks?tickers=A,B treats the comma-joined string as a single ticker and returns one empty book. The collector therefore requests each book individually. Slower collection, correct data. No user-visible difference. Get Multiple Market Orderbooks · kalshi-typescript SDK
F11 The ROI model is an unvalidated heuristic The score is a documented weighted sum of five public inputs. It has not been validated against outcomes, and the fair-value estimate is a mechanical blend rather than a forecast. The score is presented as a ranking aid with its reasons shown; the site states in several places that it is not a prediction or advice. Methodology page (model specification) · Get Market Orderbook
F12 Parallel agent sessions were active on this repository Other sessions were working in the same repo at the same time. Scopes were kept non-overlapping and recorded in COORDINATION.md; this site lives under docs/ and the collector under pipeline/, both owned by this session. If another session's site is merged later, the integration step must decide which tree Pages publishes (this site expects the Pages source path /docs). COORDINATION.md on GitHub

Values left blank on purpose

  • Kalshi demo account balance, positions, fills and settlements — no account exists, so the account panel stays empty instead of showing simulated numbers.
  • Realised fill prices for simulated trades — the simulation uses the orderbook touch, not an actual fill, and is labelled as simulated everywhere it appears.
  • Fee amounts per market — not present in the collected data (see F7).
  • Catalyst attribution for a swing — only candidate links are published (see F6).
