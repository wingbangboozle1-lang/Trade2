Standing limitations

Stated once, up front, and linked to the official page that explains each constraint

Moves the alert rule refuses are listed below, not hidden

A midpoint move of $0.10 or more on a one-sided or wide book does not become an alert, because no trade made it: on KXPRESNOMD-28-HBID the bid and ask were 0.0020 and 0.8110, so the mid could print 0.4065 while nothing traded. Those refusals are now counted and the individual ones are published in the 'Refused midpoint moves' table with the reason, so a reviewer can disagree with the rule using the same numbers.

official source ↗ · official source ↗

The model shortlist and the generator now share one gate

The page filtered the shortlist on net ROI >= 0.05 while the collector published it on model score >= 0.10, so the same feed had two definitions and the overview chat looked emptier than the data. Both sides now read one constant, alerts.model.MODEL_MIN_NET_ROI = 0.05, and the browser renders the published list rather than re-deriving it. Rows marked indicative are excluded from the shortlist on purpose: a shortlist is something a trader would act on.

official source ↗ · official source ↗

Swing alerts compared a trade price with a quote midpoint (fixed on branch arena/856e184e-trade2)

Until this fix, a >= $0.10 alert compared the candle's last-trade close with the midpoint of the current bid and ask. On KXPRESNOMD-28-HBID the last trade and the ask were 0.8110 while the bid was 0.0020, so the midpoint 0.4065 produced a 'swing' of -$0.4045 that no trade made. Alerts now compare quote mid with quote mid, require a two-sided quote narrower than $0.10, and drop stored alerts that fail that rule on the next run. The same rule removes trade prints the quotes do not support: KXPRESNOMD-28-AKLO printed 0.8030 in the hour before its alert while its bid and ask stayed at 0.0020 and 0.0030. The $0.10 narrow-spread rule is a design choice of this project, not a Kalshi rule.

The kalshi-dashboard snapshot was collected from the production host

This project is scoped to the Kalshi demo endpoint. The kalshi-dashboard collector (scripts/collect.mjs) defaulted to the production host external-api.kalshi.com. The default is now the demo host. Until the next scheduled run, the published status file still records the production base_url. The workflow step label still says 'production by default' (request logged on the coordination board).

official source ↗ · official source ↗

'OI value' is a notional figure, not dollars traded

The overview ranks markets by open_interest_fp x notional_value_dollars. Kalshi defines open interest as the number of contracts bought on the market (disregarding netting) and notional value as the value of one contract at settlement ($1.00). The product is the settlement value of open contracts. It is not dollars traded and not dollars currently at risk. The site labels it that way. Ranking by it is one reading of 'highest dollar amount'.

official source ↗

Trade-price alerts in two other pipelines are not checked against quotes (open)

The docs/ pipeline (collector/runner.py) and the kalshi-dashboard pipeline alert on consecutive trade-price closes, so the quote rule above does not cover them. The docs/ alerts currently list hourly trade-price moves such as KXRT-FUR-85 0.43 to 0.05. Those moves have not been checked against the quotes and are not changed by this branch.

Demo-account portfolio performance cannot be shown

Reading a Kalshi demo balance, fills or positions requires signed requests with an API key pair. No key is configured for this repository, so every trading figure on this site comes from the simulated ledger, not your demo account. The paper ledger is labelled SIMULATED wherever it appears.

official source ↗

No real orders are placed

Order entry is implemented (POST /portfolio/events/orders) but inert without credentials. Nothing on this site can move real or demo funds.

official source ↗

Swing alerts are detections, not executed fills

The root collector compares quote midpoints from two-sided books, using the candle-opening quote or the previous snapshot as its reference, and rejects books with a spread of $0.10 or more. Stored rows without a recognized reference_basis are dropped on the next collector run. The live desk groups repeated rows for display and marks wide-spread rows as not executable, but no alert or display badge records an order or fill. Inspect the current official order book and snapshot time before acting. The engine rule behind that wording, in full: one row per market, direction and reference bar; a repeat inside the same bar updates that row and counts itself in 'N sightings'; a later bar only opens a new row when the move has grown by a further $0.10; a reversal is always a new row; and a midpoint move the quote rule refuses is published in the refusal table below rather than dropped. The $0.10 narrow-spread rule and the folding rule are this project's design choices, not Kalshi rules — nothing here is Kalshi's fault.

official source ↗ · official source ↗ · official source ↗

News links are candidate catalysts, never confirmed causes

The brief asked for links to news that may have caused a jump. No official source maps an article to a Kalshi price move, so causality is never asserted. Two mechanisms are published instead: every ≥ $0.10 row links to the Kalshi event page — which carries Kalshi's own live news feed for that event, with its sources — and to a news search built from the event title; and the collector attaches up to six RSS headlines published within ± six hours of the alert, printed under the row as 'candidate headline, not confirmed'. A row with no result says so with the reason instead of a plausible guess, and settlement sources (AAA, CF Benchmarks, ESPN, pgatour.com) remain the only officially named references. Headline lookup needs outbound network access, so on a run without it every row shows the reason it is empty rather than a link.

official source ↗ · official source ↗ · official source ↗

A book with no resting size is shown as UNVERIFIED, not as $0.0000

For markets with no size on either side Kalshi reports yes_bid_dollars 0.0000 and yes_ask_dollars 1.0000. A full 0-to-1 book is not a price — averaging it produces a phantom $0.50 midpoint — so the collector treats it as no quote at all and the site leaves those cells blank and flagged rather than printing a price that cannot be filled. Check the linked market response to see the raw values.

official source ↗

Topic grouping of resolved markets uses the ticker prefix

GET /markets returns market objects with no series_ticker field, so a settled market cannot be filed under a topic from that response alone. The series ticker is recovered from the market ticker prefix, which is Kalshi's own naming convention, and the API value is preferred whenever it is present. Settled markets outside the five tracked topics are counted separately rather than dropped without trace.

official source ↗

The demo feed prints alternating trades on some markets

On several demo markets the traded price oscillates between two levels every minute while the quoted order book never changes. For example the one-minute candles for KXPRESNOMD-28-AKLO alternate between $0.8030 and $0.0030 while the book stays at $0.0020 x $0.0030 for the whole window. A move the book did not make is a trade print rather than a market move, so the model rejects it and it is listed on this page.

official source ↗

Historical swing-chat rows were duplicated and midpoint-based (fixed 2026-11-20)

Before this revision the swing chat could show the same sustained move once per collector run (observed: 29 rows over only 3 tickers) and could alert on the midpoint of a $0.80-wide spread. Alerts are now deduplicated to one row per market per reference window per direction and measured on a depth-aware price basis (tight-book mid, else last trade). Rows that still carry a wide spread are labelled 'thin book' rather than dropped. See COORDINATION.md request R-D-01 for the evidence.

official source ↗

Snapshot freshness is best-effort

The collector runs on a 5-minute GitHub Actions schedule, which GitHub itself documents as best-effort and subject to lag. A snapshot can therefore be older than its nominal cadence; the topbar computes and shows the snapshot's age in your browser so staleness is always visible.

official source ↗

Live streaming uses polling, not the WebSocket

The documented demo WebSocket requires the same signed handshake as REST, so without credentials the site polls the public REST API. Prices can lag by the poll interval; the page shows the age of every snapshot.

official source ↗

The model's ROI is a screen, not a validated edge

Signals are ranked by modelled edge after Kalshi's published taker fee. No claim of profitability is made, and the performance table publishes every loss alongside every win once trades settle.

official source ↗

Taker fees use a multiplier of 1 for every series

Kalshi's quadratic taker fee is round-up(M x 0.07 x C x P x (1-P)), and the published schedule sets M per series — 0 for fee-free series such as the yearly Bitcoin and Ether ranges, 2 for uncorrelated combos. The simulated ledger applies M = 1 everywhere instead of reading each series' own value (collector/engine.py calls kalshi_fee(price, contracts) with the default multiplier at both the entry and the exit site, although collector/topics.py already caches fee_multiplier per series). This was checked against the live demo record for KXBTCY on 2026-11-20, which returns fee_multiplier 1, so the fee shown for the open position on that series is correct for the demo environment — the exposure is to series whose demo multiplier is not 1, and to production, where the same series is listed at 0. Fees on those rows would be mis-stated until the engine threads the value through.

official source ↗ · official source ↗

Each run tracks a ranked slice, not every market

The collector reads a bounded number of the highest-value markets per topic inside a fixed time budget, and reports the counts it actually read plus anything it had to skip.

official source ↗

Three scheduled workflows collect the same data, and the most frequent one rarely runs

Verified from the repository and the Actions API, not inferred. Three workflows collect from the demo API and commit to `main`: `kalshi-dashboard.yml` (cron `*/5`), `collector.yml` (`*/15`) and `dashboard.yml` (`*/30`). The `*/5` one groups its runs under `concurrency: collect` with `cancel-in-progress: false`, and on a repository this busy a run in that group spends longer than five minutes than not — so new runs replace queued ones instead of waiting. Two runs of it on 2026-11-20 ended `cancelled` after 17 s and 43 s (runs 44804717748 and 44804612803), while the `collector` workflow triggered by the same merge completed in 19 s.
