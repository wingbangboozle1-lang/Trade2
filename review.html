Moves the alert rule refuses are listed below, not hidden

A midpoint move of $0.10 or more on a one-sided or wide book does not become an alert, because no trade made it: on KXPRESNOMD-28-HBID the bid and ask were 0.0020 and 0.8110, so the mid could print 0.4065 while nothing traded. Those refusals are now counted and the individual ones are published in the 'Refused midpoint moves' table with the reason, so a reviewer can disagree with the rule using the same numbers.

Swing alerts compared a trade price with a quote midpoint (fixed on branch arena/856e184e-trade2)

Until this fix, a >= $0.10 alert compared the candle's last-trade close with the midpoint of the current bid and ask. On KXPRESNOMD-28-HBID the last trade and the ask were 0.8110 while the bid was 0.0020, so the midpoint 0.4065 produced a 'swing' of -$0.4045 that no trade made. Alerts now compare quote mid with quote mid, require a two-sided quote narrower than $0.10, and drop stored alerts that fail that rule on the next run. The same rule removes trade prints the quotes do not support: KXPRESNOMD-28-AKLO printed 0.8030 in the hour before its alert while its bid and ask stayed at 0.0020 and 0.0030. The $0.10 narrow-spread rule is a design choice of this project, not a Kalshi rule.

'OI value' is a notional figure, not dollars traded

The overview ranks markets by open_interest_fp x notional_value_dollars. Kalshi defines open interest as the number of contracts bought on the market (disregarding netting) and notional value as the value of one contract at settlement ($1.00). The product is the settlement value of open contracts. It is not dollars traded and not dollars currently at risk. The site labels it that way. Ranking by it is one reading of 'highest dollar amount'.

A flat $0.10 threshold is not the same distance on every market

A contract on a one-cent grid needs ten ticks to move $0.10; a contract quoted 0.01 / 1.00 needs one tick. The largest open-interest market in this snapshot, KXPRESNOMD-28-RW, trades on a 0.0010 step, so its midpoint needs a hundred ticks to clear the threshold, while an empty demo book clears it on a single tick. The alert rule is correct but the number is not comparable across markets. Recommendation (not yet implemented, needs a per-row price_ranges source link and a payload change owned by other sessions): show 'approx N ticks' on each alert row. A one-minute candle close can be a single stray quote

The collector measures each swing against the previous completed 1-minute candle's yes_bid / yes_ask closes. One minute is the finest official bar (period_interval must be 1, 60 or 1440), so it cannot be shortened. But a candle close is an instantaneous quote: the KXPRESNOMD-28-BOBA daily bar ending 2026-11-21T05:00Z closed with yes_bid 0.0010 against yes_ask 0.8820, one stray NO bid at 0.118 on a two-cent market. The quote rule refuses the resulting $0.877 'move' (see 'Refused midpoint moves'), which is the right outcome, but the check fires only after the number exists. Recommendation: cross-check with the documented price.previous_dollars field already present in every candle. Logged as R-F3-1; not implemented because it changes the shared alert payload.

The live pulse measures a different reference than the collector

The panel called 'Live pulse' on the live desk re-reads the order books from the visitor's browser every 45 s and compares each reading with the previous one, so a row there means 'the book moved $0.10 between two readings of this tab', not 'the collector measured a move against Kalshi's candle'. The previous-snapshot fallback was dead until 2026-11-21 (fixed, session arena-27de8294)

Two bases turn a book into an alert: the official 1-minute candle quote (candle_quote_mid) when Kalshi published one, and the previous snapshot's quoted mid (previous_snapshot_mid) when it did not. Swing alerts are detections, not executed fills

The root collector compares quote midpoints from two-sided books, using the candle-opening quote or the previous snapshot as its reference, and rejects books with a spread of $0.10 or more. Stored rows without a recognized reference_basis are dropped on the next collector run. The live desk groups repeated rows for display and marks wide-spread rows as not executable, but no alert or display badge records an order or fill. Inspect the current official order book and snapshot time before acting. The engine rule behind that wording, in full: one row per market, direction and reference bar; a repeat inside the same bar updates that row and counts itself in 'N sightings'; a later bar only opens a new row when the move has grown by a further $0.10; a reversal is always a new row; and a midpoint move the quote rule refuses is published in the refusal table below rather than dropped. The $0.10 narrow-spread rule and the folding rule are this project's design choices, not Kalshi rules — nothing here is Kalshi's fault.

News links are candidate catalysts, never confirmed causes

The brief asked for links to news that may have caused a jump. No official source maps an article to a Kalshi price move, so causality is never asserted. Two mechanisms are published instead: every ≥ $0.10 row links to the Kalshi event page — which carries Kalshi's own live news feed for that event, with its sources — and to a news search built from the event title; and the collector attaches up to six RSS headlines published within ± six hours of the alert, printed under the row as 'candidate headline, not confirmed'. A row with no result says so with the reason instead of a plausible guess, and settlement sources (AAA, CF Benchmarks, ESPN, pgatour.com) remain the only officially named references. Headline lookup needs outbound network access, so on a run without it every row shows the reason it is empty rather than a link.

A book with no resting size is shown as UNVERIFIED, not as $0.0000

For markets with no size on either side Kalshi reports yes_bid_dollars 0.0000 and yes_ask_dollars 1.0000. A full 0-to-1 book is not a price — averaging it produces a phantom $0.50 midpoint — so the collector treats it as no quote at all and the site leaves those cells blank and flagged rather than printing a price that cannot be filled. Topic grouping of resolved markets uses the ticker prefix

GET /markets returns market objects with no series_ticker field, so a settled market cannot be filed under a topic from that response alone. The series ticker is recovered from the market ticker prefix, which is Kalshi's own naming convention, and the API value is preferred whenever it is present. Settled markets outside the five tracked topics are counted separately rather than dropped without trace.

The fee PDF and the demo API disagree about some series' multiplier

Kalshi's quadratic taker fee is round-up(M x 0.07 x C x P x (1-P)), and the published schedule sets M per series — 0 for fee-free series such as the yearly Bitcoin and Ether ranges, 2 for uncorrelated combos. The simulated ledger and the engine read each series' own fee_multiplier and fee_type from the official GET /series response (alerts.fee_params) and print that basis on every trade row, falling back to the schedule's default M = 1 only when a series lookup is unavailable. What remains unresolved is a source disagreement, not a code path: the PDF table lists KXBTCY at 0/0 while the demo GET /series/KXBTCY returned fee_multiplier 1 on 2026-11-20, and this project follows the API field. In production the same series is listed at 0, so fees there would differ from the demo ledger.

Snapshot cadence is best-effort: three scheduled workflows, one queue

Verified from the repository and the Actions API, not inferred. Three workflows collect from the demo API and commit to `main`: `kalshi-dashboard.yml` (cron `*/5`), `collector.yml` (`*/15`) and `dashboard.yml` (`*/30`). On 2026-11-20 the `*/5` workflow grouped all of its runs under one `concurrency: collect` group, and two of them ended `cancelled` after 17 s and 43 s (runs 44804717748 and 44804612803) while the `collector` workflow triggered by the same merge completed in 19 s. R-1E3-1 (applied 2026-11-21 via PR #60) keys that group by event name now (`collect-schedule` vs `collect-push`), so a queued schedule run is only ever replaced by a newer schedule run. What remains is the repo-wide effect: this repository runs many workflows per minute, so queue pressure — not the concurrency key — still decides the real cadence. Consequence for a trader: the published snapshot's age is what the top bar shows, not five minutes. The queueing reading is this project's interpretation of the workflow configuration and the recorded runs, not a confirmed GitHub guarantee — see the concurrency documentation for the rule.
