Standing limitations

Stated once, up front, and linked to the official page that explains each constraint

Swing alerts once compared a trade price with a quote midpoint (fixed; verified live 2026-11-20)

Until this fix, a >= $0.10 alert compared the candle's last-trade close with the midpoint of the current bid and ask. On KXPRESNOMD-28-HBID the last trade and the ask were 0.8110 while the bid was 0.0020, so the midpoint 0.4065 produced a 'swing' of -$0.4045 that no trade made. Alerts now compare quote mid with quote mid and only publish a move that can be dealt on: both quotes two-sided, and the spread strictly below $0.10. The requirement threshold itself is unchanged at $0.10 and is never raised; what is gated is dealability, because a book wider than the threshold can only move its mid by having a side pulled. Stored rows that cannot show a quote basis are dropped on the next run. The same rule removed KXPRESNOMD-28-AKLO, whose 0.8030 was a trade print on a book quoted 0.0020 / 0.0030. The $0.10 narrow-spread rule is a design choice of this project, not a Kalshi rule; the full rule is published at methodology.html#alert-rule. Confirmed on a live demo run at 2026-11-20T19:18Z: the feed went from 29 phantom rows to 0, and the model chat carried a real scored signal.

The kalshi-dashboard snapshot was collected from the production host

This project is scoped to the Kalshi demo endpoint. The kalshi-dashboard collector (scripts/collect.mjs) defaulted to the production host external-api.kalshi.com. The default is now the demo host. Until the next scheduled run, the published status file still records the production base_url. The workflow step label still says 'production by default' (request logged on the coordination board).

'OI value' is a notional figure, not dollars traded

The overview ranks markets by open_interest_fp x notional_value_dollars. Kalshi defines open interest as the number of contracts bought on the market (disregarding netting) and notional value as the value of one contract at settlement ($1.00). The product is the settlement value of open contracts. It is not dollars traded and not dollars currently at risk. The site labels it that way. Ranking by it is one reading of 'highest dollar amount'.

Trade-price alerts in two other pipelines are not checked against quotes (open)

The docs/ pipeline (collector/runner.py) and the kalshi-dashboard pipeline alert on consecutive trade-price closes, so the quote rule above does not cover them. The docs/ alerts currently list hourly trade-price moves such as KXRT-FUR-85 0.43 to 0.05. Those moves have not been checked against the quotes and are not changed by this branch.

Demo-account portfolio performance cannot be shown

Reading a Kalshi demo balance, fills or positions requires signed requests with an API key pair. No key is configured for this repository, so every trading figure on this site comes from the simulated ledger, not your demo account. The paper ledger is labelled SIMULATED wherever it appears.

official source ↗

No real orders are placed

Order entry is implemented (POST /portfolio/events/orders) but inert without credentials. Nothing on this site can move real or demo funds.

Alert rows can repeat, and midpoints may not be executable

The alert engine compares book midpoints between reference bars, so one sustained >= $0.10 move can fire again on each consecutive snapshot: the 2026-11-20 18:41 UTC snapshot carried 29 raw alert rows over only 3 tickers, including a row whose quoted book was $0.002 bid / $0.811 ask against a $0.4065 midpoint — a spread wider than the alert threshold itself, so the midpoint was not an executable price. Until the engine-side fix lands (coordination request R-D-01), the live desk groups identical repeats client-side (xN badge) and marks rows whose YES spread is >= $0.10 as not executable; raw rows are never deleted from the snapshot. Treat each row as a detection event, not a tradable quote.

No news article is attributed to a price move

The brief asked for links to news that may have caused jumps. No official source maps articles to Kalshi price moves, so guessing one would be fabrication. Instead every alert links to the market itself and the series page lists Kalshi's own settlement sources (AAA, CF Benchmarks, ESPN, pgatour.com), which are the official pages that explain the underlying.

official source ↗

Live streaming uses polling, not the WebSocket

The documented demo WebSocket requires the same signed handshake as REST, so without credentials the site polls the public REST API. Prices can lag by the poll interval; the page shows the age of every snapshot.

official source ↗

The model's ROI is a screen, not a validated edge

Signals are ranked by modelled edge after Kalshi's published taker fee. No claim of profitability is made, and the performance table publishes every loss alongside every win once trades settle.

official source ↗

Each run tracks a ranked slice, not every market

The collector reads a bounded number of the highest-value markets per topic inside a fixed time budget, and reports the counts it actually read plus anything it had to skip.

official source ↗

Fee-schedule rounding prose and its own table disagree

The fee PDF says to round so that 'fee + positionCost is rounded to a centicent', but its published table is reproduced exactly by rounding the fee alone up to the cent. The table is used as the oracle, because it matches every one of the 42 published rows.
