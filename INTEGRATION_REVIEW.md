## 5. R-D-01 — repeated / non-executable midpoint alerts (adopted and fixed)

Evidence (session 0b2d2a2a's audit, reproduced in this snapshot before the fix):
29 alert rows over 3 tickers, same rows repeated per run; a row triggered on a
`$0.002 / $0.811` book (mid `$0.4065`) that never traded at the midpoint.

Root causes found line-by-line:

1. `collector/alerts.py` keyed alerts by `ticker + run timestamp` — every run
   minted a new id for the same move, and the merge kept all of them.
2. The swing rule measured the raw midpoint of any book, however wide.
3. The site rendered rows without labelling their basis, and showed no snapshot
   age.

Fixes (each with regression tests in `tests/test_alerts.py`, 13 cases):

* **Depth-aware price basis** (`price_basis`): mid counts only when both sides
  quote and spread ≤ $0.20; otherwise the last traded price; a single-sided
  quote is the last resort; nothing measurable ⇒ no alert. The phantom
  `0.811 → 0.4065` case cannot fire any more (tested).
* **Dedupe** (`dedupe_alerts`): one row per market/reference-window/direction
  (largest move wins), plus one row per identical `previous → current` move
  within 24 h. Applied in the collector **and** at build time
  (`tools/dedupe_alerts.py`); the published buffer was folded 32 → 9 rows
  offline so this merge ships clean pages, and `ALERTS_VERSION = 3` discards
  legacy rows on the next run.
* **Labels**: every alert row now carries `basis` / `spread` / `thin_book`; the
  chats and chart annotations show a "thin book"/"one-sided book" badge instead
  of dropping rows.
* **Snapshot age**: topbar computes `· age N min` in the browser; ≥ 15 min is
  highlighted (GitHub's own schedule is best-effort — documented).
* **Flagged for Review**: `review.html` gains (a) a generated irregularity per
  wide-spread alert still in the snapshot, linking its order book, (b) standing
  items for the historical behaviour (fixed) and snapshot freshness.
