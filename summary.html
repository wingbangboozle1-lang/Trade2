Executive summary

What this dashboard can confirm, how it works, and what remains deliberately unconnected.

At a glance

Market Desk is a GitHub Pages-ready, client-side Kalshi demo monitor. It scans open events from the recommended demo Trade API, filters the requested topics (gas prices, elections, culture, crypto, golf), ranks rows by a calculated open-interest value (open_interest_fp × notional_value_dollars) when both official fields are available, and uses blank/flagged cells instead of guessing missing values. The API defines notional_value_dollars as one contract’s settlement value, so the product is not traded-dollar volume. Each market row links to its official demo API resource.

How the site gets its numbers: a scheduled collector reads the recommended demo Trade API, writes a verified snapshot, and a build step pre-renders every page from that snapshot. The published pages are therefore complete and correct with JavaScript switched off, and the front-end layer only adds live polling on top. The page prints the age of the snapshot it is showing, so a quiet schedule can never be mistaken for a live feed.

Sudden moves of at least $0.10 in either direction are recorded against a measured reference price — the open of the current five-minute candle where Kalshi publishes one, otherwise the previous observation — so a gradual drift that crosses the threshold is still caught. The live desk plots real Kalshi candlesticks and the live order book implied mid, with seconds, minutes and hours windows, and lists the resting contracts at each price. Every ≥ $0.10 row links to the Kalshi event page, which carries Kalshi's own news feed for that event, and to a news search for the event title. Neither link asserts that an article caused the move.

Two alert chats run side by side: every observed threshold move, and a shortlist filtered to the signals the model scores as high ROI after Kalshi's published taker fee. The shortlist is a screen, not an expected-return model, and it is not a prediction of profit. Simulated trades are executed against live public prices by a server-side paper ledger that stores entry assumptions, fees, timestamps and resolved outcomes; it never submits a Kalshi order, and its results — including every loss — are published on the trades page.

Operational design and next steps

  • Use WebSockets for genuine low-latency ticker/orderbook updates after a secure authenticated service is available. Current static-only polling cannot promise sub-second alert delivery.
  • Add a server-side, credential-safe service for demo account balance, order status, fills, portfolio history, and optionally demo order placement; keep private signing keys out of GitHub Pages and browser storage.
  • Persist quote history in a database if alerts need continuity across devices, browsers, deployments, or page closures. The collector already keeps a rolling history on disk; a database would make it queryable and longer-lived.
  • For jump context, keep pointing at the Kalshi event page and the news search; a human-reviewed headline feed would be stronger, but no causal link is inferred or fabricated by this dashboard.
  • Validate the category matcher against current open demo event data and review false positives/omissions. It scans at most four pages (up to 800 events) per refresh, so completeness is not claimed.
  • For strategy evaluation, store entry/exit assumptions, fees, fill/slippage rules, timestamps, and resolved outcomes; separate in-sample screening from out-of-sample results. The current shortlist has no demonstrated ROI.

The full prioritised list of improvements is published on the suggestions page, and everything that could not be verified is published on the Flagged for review page.
